# ESP32-S3 AMOLED 车机 显示故障根因记录

记录时间：2026-11-02
涉及硬件：微雪 ESP32-S3-Touch-AMOLED-2.16（CO5300 QSPI 480×480 / 8MB PSRAM / 16MB Flash）
涉及代码：小智 xiaozhi-esp32 工程 + pet_anim 宠物动画组件
结论一句话：**全部是软件问题，没有硬件损坏**。核心是三条——坐标语义搞错、SPI 面板 IO 非线程安全、小智自带省电定时器会往动画上盖 UI 并自动关机。

---

## 一、按现象对应根因（速查表）

| 现象 | 根因 | 关键代码位置 |
|---|---|---|
| 一条条白色横杠 | `esp_lcd_panel_draw_bitmap` 结束坐标是**排他**的，传 `w-1` 少发一整行 | 板级 `pet_flush_cb` |
| 画面只剩顶部一条 + 定格 + 整机卡死 | 宠物任务与 LVGL 并发使用同一个 `esp_lcd_panel_io_spi`，事务池记账被打乱 | 板级 flush 加 `lvgl_port_lock` |
| 正中间一套灰色横杠（对话气泡框） | 省电定时器 60 秒触发 `SetPowerSaveMode(true)` → 内部 `SetChatMessage("system","")` 重绘灰底气泡 | `InitializePowerSaveTimer()` |
| 开机一会儿自动关机 | 同一个省电定时器 300 秒触发 `pmic_->PowerOff()` | 同上 |
| 每 5 秒重启一轮 | 换宠物包时只 `delay(300ms)` 就 free 旧 buffer，播放任务还在读 | `pet_anim_pull` |
| 全白屏、什么都没有 | 本地包加载失败仍无条件 `lvgl_port_stop()` | `InitializePetAnim` |
| 触摸失效 + 横杠 | 宠物 12fps 连续抢 `lvgl_port_lock` 全屏送屏，把 LVGL 任务饿死到 30s 超时 | 早期 flush 实现 |
| 摇动、说话都不切画面 | 设备当时在复位循环里，根本没进入正常时序；不是检测逻辑错 | 见第五节 |

## 二、白色横杠（第一次定位）

### 现象
屏幕出现均匀间隔的白色横条，内容能隐约看到但整体被横条破坏。改分块大小、改双缓冲都没用。

### 根因
`esp_lcd_panel_draw_bitmap(panel, x0, y0, x1, y1, data)` 的 `x1 / y1` 是**排他坐标**（不包含该行/列），不是"最后一行的索引"。

CO5300 驱动里算传输长度是：

```c
// managed_components/espressif__esp_lcd_co5300/esp_lcd_co5300_spi.c
len = (x_end - x_start) * (y_end - y_start) * 2;
```

传 `w-1 = 479` 就变成"只发 479 列"，而面板窗口开的是 480 列 —— **每一块都比窗口少一整行**，面板填不满，剩下的就是上一帧残留的白条。所以怎么调分块都修不好，因为它不是时序问题。

参考小智官方 LVGL 端口的正确用法（`esp_lvgl_port_disp.c:758` 用的是 `offsetx2 + 1`）。

### 修法
```c
// 错
esp_lcd_panel_draw_bitmap(panel, 0, y, w - 1, y + n - 1, buf);
// 对
esp_lcd_panel_draw_bitmap(panel, 0, y, w, y + n, buf);
```

### 同时修掉的隐患
`esp_lcd_panel_io_tx_color` 内部是 `spi_device_queue_trans(portMAX_DELAY)` —— **塞进队列就返回**，DMA 还在跑函数已经回来了。板级 `io_config.trans_queue_depth = 10`，如果只用一块 linebuf，下一块数据会覆盖正在被 DMA 读的内存，送出去就是错行数据。

→ 改为双缓冲条带（`s_pet_strip[2][480 * 20]`，内部 SRAM，19.2KB × 2）交替使用。

## 三、定格 + 只剩顶部一条 + 整机卡死（最严重的一个）

### 现象
画面顶部显示一条正常动画，往下全是蓝色/纯色，然后彻底定格；串口完全静默，触摸无效，只能重新上电。

### 日志证据
```
recycle spi transactions failed
send color data failed
```

### 根因
`esp_lcd_panel_io_spi` **不是线程安全的**。它内部用共享的 `trans_pool` 和 `num_trans_inflight` 记账，两个任务同时调用 `draw_bitmap` 时事务池记账被搞乱，报 `recycle failed` 之后队列永久卡死，播放任务阻塞在第一帧里再也不返回。

小智的 LVGL 任务和宠物动画任务正好是两个任务，都在往同一块面板送数据。

### 修法
每帧送屏前拿 LVGL 锁串行化，拿不到就丢这一帧（绝不阻塞播放任务）：
```c
if (!lvgl_port_lock(1000)) return ESP_ERR_TIMEOUT;   // 1 秒拿不到锁，丢帧
// ... 送屏 ...
lvgl_port_unlock();
```
因为条带方案一帧只有几十次 draw、持锁时间很短，不会反过来饿死 LVGL。

## 四、灰色横杠与自动关机（小智自带逻辑，最隐蔽）

### 现象
屏幕正中一套半透明灰底的"横杠"，位置固定、内容不随动画变化。另外，静置一段时间后设备会自己关机。

### 根因
板级 `InitializePowerSaveTimer()` 原本是：
```c
power_save_timer_ = new PowerSaveTimer(-1, 60, 300);
```
- **60 秒**无操作 → `GetDisplay()->SetPowerSaveMode(true)`，而 `LcdDisplay::SetPowerSaveMode` 内部会调 `SetChatMessage("system", "")` 往对话区写一条空消息，LVGL 于是在动画正中间画出那块半透明灰底的对话气泡框 —— 就是用户看到的"一套灰色横杠"。
- **300 秒** → `OnShutdownRequest` 里 `pmic_->PowerOff()`，**直接关机**。这是"一开一关就退出"的元凶之一。

车机是常亮常开的设备，这两条逻辑都不该存在。

### 修法
```c
power_save_timer_ = new PowerSaveTimer(-1, -1, -1);   // 三段全关，且不再 SetEnabled
```
另外把所有 LVGL 顶层控件加 `LV_OBJ_FLAG_HIDDEN` 兜底，即使有残留刷新也画不出东西。

## 五、反复重启（每 5 秒一轮）

### 现象
串口日志时间戳反复从 `1698` 重新开始，每 5 秒一轮"初始化 LVGL → 加载宠物包 → 播 idle → LVGL 停 → 又重启"。复位码 `rst:0x15 (USB_UART_CHIP_RESET)`。

### 根因（两条叠加）
1. **换包释放缓冲的竞态**：`pet_anim_pull` 拉到新包后只 `vTaskDelay(300ms)` 就 `free` 旧 `pack_buf`，但播放任务是异步退出的，可能还在读这块内存 → 访问已释放内存 → 崩溃重启。
2. **USB 供电不足**：WiFi 发射 + AMOLED 峰值电流同时上来，USB 口/Hub 拉不住就 brownout。换到 Mac 机身直连口、换数据线后消失。

### 修法
- 新增 `pet_anim_wait_stopped(3000)`，等播放任务真的退出（`s_ctx.task == NULL`）才换包，超时则放弃这次换包。
- 开机顺序改为「先 `lvgl_port_stop()` + 150ms，再 `pet_anim_start()`」，避免开头两者抢总线。
- 降低网络请求频率（上报 5 秒一次、比包 30 秒一次），削掉 WiFi 电流峰值。
- 打开 `esp_reset_reason()` 打印，以后能直接区分 brownout / panic / 看门狗。

## 六、全白屏

### 根因
`InitializePetAnim` 里原来是「不管包有没有加载成功，都调 `lvgl_port_stop()`」。结果：LVGL 界面被停掉、宠物动画又因为包加载失败没起来 → 屏幕全白，什么信息都没有。

### 修法
只有 `pet_anim_load_pack_file()` 返回 `ESP_OK` 才停 LVGL；失败就保留小智界面并打错误日志，等 `pet_pull` 拉到包后再切。

## 七、触摸失效

### 根因
早期实现里宠物任务 12fps 连续调用 `lvgl_port_lock(0)`（即 `portMAX_DELAY`）做全屏送屏，LVGL 任务永远抢不到锁，最后 `Display::Lock` 30 秒超时，触摸随之失效。

### 修法
- 动画播放期间 `lvgl_port_stop()`，宠物用自己的专用互斥锁 `s_pet_mux`；
- 后来改为统一用 `lvgl_port_lock(1000)` 串行化（一帧一次 draw，持锁极短）。

代价：**测试期间触摸不可用**（LVGL 已停）。语音交互不受影响。

---

## 八、"摇动 / 说话都不切画面"

这一条最初怀疑是检测逻辑写错，逐层排查后**排除**：

- 说话链路：TTS 开始 → `SetDeviceState(kDeviceStateSpeaking)` → 状态监听器 → `pet_anim_set_talking(true)` → 播放任务切 `talk` 段，每一环都在。
- IMU：日志确认 `WHO_AM_I = 0x05`、标定成功（g ≈ (0, 0, 1.02)，sigma ≈ 0.003），摇动判据公式正确。
- 资源包：直接解析服务器上的 `pet.pack`，`idle(60帧) / run(60) / brake(48) / talk(36)` 四段齐全，204 帧全部是标准 480×480 JPEG，帧内容各不相同。

**真正的解释**：设备当时处在 5 秒一轮的复位循环里（第五节），根本没进入"联网 → 唤醒 → 对话"的正常时序；即使偶尔跑起来，画面也会在第一帧送屏里被 SPI 事务池卡死（第三节）。所以不是不切，是切了也看不见。

最终修完后日志确认全部生效：
```
心跳: 60 帧 / 11.8 s = 5.1 fps
→ run（motion=1 sigma=0.079）      摇动切跑步段
→ idle（sigma=0.004）              停下切回待机
→ talk（talk=1）                   说话切对话段
emotion happy → happy (5000ms)     情绪联动
```

## 九、排除掉的一条路：PSRAM 直连 DMA

一度想让 SPI DMA 直接从 PSRAM 读整帧（省掉 460KB 拷贝和 bswap），给面板 IO 开了 `flags.psram_dma_direct = true`。

**结果：屏幕中间出现灰色横条并最终卡死。**

依据在 LVGL 端口自己的注释里（`main/display/lcd_display.cc:173`）：
```
// SPI LCD still needs an internal DMA bounce buffer for PSRAM sources.
// A full-frame transfer (~150KB) cannot allocate that bounce buffer, so ...
```
即：SPI 屏从 PSRAM 取数据必须先有内部 DMA bounce buffer，整帧 150KB 分配不出来。所以 LVGL 自己一直用「内部 SRAM + 480×20 条带」。**结论：不要开 `psram_dma_direct`，跟随 LVGL 的条带方案。**

## 十、最终定案的送屏实现

```
条带 480×20（19.2KB，内部 SRAM，双缓冲交替）
  ↓
每帧持 lvgl_port_lock(1000)（拿不到就丢帧）
  ↓
esp_lcd_panel_draw_bitmap(panel, 0, y, w, y + n, dst)   ← 排他坐标
  ↓
字节序：JPEG 解码时 swap_color_bytes = 1（面板大端），避免 CPU 做 460KB bswap
```

实测：零 SPI 错误、稳定 5 fps、IMU / 情绪 / talk 联动全部正常。

## 十一、经验条目（下次别再踩）

1. `esp_lcd_panel_draw_bitmap` 的 `x_end / y_end` 是**排他**坐标。传最后一列索引会导致"少一行"，现象是均匀横杠。
2. `esp_lcd_panel_io_spi` 非线程安全。任何第二个任务往同一面板送数据，都必须和 LVGL 串行化。
3. `tx_color` 是排队即返回，单缓冲分块送屏一定会被下一块覆盖，必须双缓冲。
4. 不要给 SPI 屏开 `psram_dma_direct`。
5. 小智的 `PowerSaveTimer` 会在 60 秒画对话气泡、300 秒直接关机，车机场景必须关掉。
6. 换资源包必须等播放任务真正退出才 free 旧缓冲。
7. 本地包加载失败时不要停 LVGL，否则全白屏无从定位。
8. AMOLED + WiFi 峰值电流大，USB 供电不稳会表现为"随机重启"，优先怀疑线材和 Hub。
9. 排查时先分清"设备有没有在正常时序里"——一次复位循环能伪造出十几个看似独立的 bug。
