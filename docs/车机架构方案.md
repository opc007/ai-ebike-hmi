# AI 智能两轮车车机改造 · 架构方案 v0.1

> 硬件已确认：交互板为微雪 ESP32-S3-Touch-AMOLED-2.16（ESP32-S3R8 / 8MB Octal PSRAM / 16MB Flash），
> 已带小智 AI 固件 v2.4.0。车辆板待选型。

---

## 一、结论

**分两块 ESP32 是对的**，但原方案有三处要调整，其中第一处涉及安全责任归属。

| # | 原设想 | 调整后 | 原因 |
|---|---|---|---|
| 1 | 交互板读车辆板数据"了解车内情况" | 车辆板是**唯一数据权威源**，交互板只做展示，不自行推算电量/车速 | 两处各自算 SOC 必然打架，用户会看到两个矛盾的数 |
| 2 | 小程序是"总控" | 小程序是**管理面**，不做实时控制通道 | 地库没信号 = 开不了锁，这是产品级致命伤 |
| 3 | 交互板直接接 5V 常电 | 交互板 5V 由车辆板控制通断 | 拔钥匙后交互板要能真断电，否则亏电瓶 |

## 二、单板 vs 双板

| 维度 | 单板（全放 AMOLED 板） | 双板（交互 + 车辆） |
|---|---|---|
| 可行性 | 勉强，IO 只剩 6 个空闲脚 | 充裕 |
| 故障影响 | 车机死机 = 开不了锁、看不到车况 | 车机死机不影响解锁与行驶 |
| 电气噪声 | 电磁锁感性负载反电动势灌进 codec，语音会带嗡声 | 光耦/继电器隔离，互不干扰 |
| 固件迭代 | 宠物皮肤和锁控逻辑同一份固件，OTA 风险叠加 | 分层 OTA，交互层可天天空翻车 |
| 成本 | 省一颗 MCU（约 ¥12） | 多一颗 C3 + 保护电路 |
| 布线 | 线束集中车头 | 多一条 UART 线 |

**建议双板。** 单板唯一的优势是省十几块钱，代价是把"骑不了车"和"看不了宠物"绑成同一个风险。
真要单板，也应该是"交互板 + I2C 扩展 IO"，且大电流控制仍必须外挂继电器模块。

## 四、板间通信协议

物理层：UART，115200 8N1，TTL 3.3V，双向。线束走屏蔽双绞，两端共地但串 22Ω 电阻抑制地环流。

### 帧格式

```
偏移   长度   字段
0      2     帧头 0xAA 0x55
2      1     协议版本 0x01
3      1     命令码
4      1     序号 seq（0-255 回绕）
5      1     负载长度 len（0-64）
6      len   负载
6+len  2     CRC16-MODBUS（小端，覆盖偏移 2 至 6+len-1）
```

### 命令表

| 命令码 | 名称 | 方向 | 负载 |
|---|---|---|---|
| 0x01 | 状态上报 | 车 → 交 | 电压(mV) 电流(mA) SOC(%) 车速(0.1km/h) 里程(m) 锁态 故障位 |
| 0x02 | 心跳应答 | 交 → 车 | 空 |
| 0x10 | 开锁请求 | 交 → 车 | 请求 ID(2B) + 来源(语音/触摸/远程) |
| 0x11 | 开锁应答 | 车 → 交 | 请求 ID(2B) + 结果码 + 耗时(ms) |
| 0x12 | 落锁请求 | 交 → 车 | 同上 |
| 0x20 | 参数读写 | 双向 | 键(2B) + 值 |
| 0x30 | 固件分片 | 交 → 车 | 偏移(4B) + 数据 |

状态上报频率 1Hz；开锁请求超时 2s 未应答即判定失败并回滚 UI。
所有控制类命令必须带请求 ID，应答原样回传，防止乱序误判。

### 心跳降级

| 心跳丢失时长 | 交互板行为 |
|---|---|
| < 1s | 正常 |
| 1–3s | 数据角标变黄，提示「数据延迟」 |
| > 3s | 仪表进入「车辆离线」占位，**禁用开锁按钮**，语音播报一次 |
| > 30s | 只保留时钟与宠物，云端 AI 继续可用 |

## 五、IO 分配

### 交互板（ESP32-S3 AMOLED）—— 现状已占满

```
0                  BOOT
1,2,3,41           TF 卡（不用可回收 4 个）
4,5,6,7,38,12,39   屏 QSPI
8,9,10,42,45,46    音频 I2S + 功放使能
11,40              触摸
13                 RTC 中断
14,15              共享 I2C（可挂外部器件）
16,18              SYS_OUT / Key3
17,21              IMU 中断
19,20              原生 USB
26–32              Flash 独占
33–37              Octal PSRAM 独占 ← 不可用
43,44              UART0
```

**空闲：22、23、24、25、47、48（6 个）**
用途：UART 到车辆板占 2 个（TX/RX），剩 4 个留作备用或 I2C 中断。
扩展优先走 14/15 的 I2C（注意地址冲突，现有 0x34/0x51/0x6B/0x32 等）。

### 车辆板（ESP32-C3 建议）

| 用途 | 数量 | 备注 |
|---|---|---|
| UART → 交互板 | 2 | 主通道 |
| CAN TX/RX | 2 | 需 SN65HVD230 |
| RS485 DE/RE | 1 | 需 MAX3485 + 隔离 |
| 霍尔测速 | 1 | PCNT 硬件计数 |
| ACC 检测 | 1 | 分压 + 光耦 |
| 电磁锁驱动 | 1 | 经光耦驱 MOS/继电器 |
| 喇叭 / 灯光 | 2 | 同上 |
| 电池电压采样 | 1 | ADC，分压后 |
| 电流采样 | 1 | INA226 走 I2C 更准 |
| 交互板 5V 高边开关 | 1 | 电源主控 |
| **合计** | **13** | C3 可用约 13–15，**刚好卡满，无冗余** |

> C3 太紧的话，车辆板直接上 ESP32-S3-Zero 或 C6，多留 6–8 个脚给后续扩展（GNSS、4G、指纹）。

## 六、电源架构

```
48–72V 电池
  │
  ├─ 保险丝 5A → TVS(SMBJ58A) → 防反 MOS
  │
  └─ 隔离 DC-DC（48–72V → 12V，≥3A）
        │
        ├─ 12V 轨：电磁锁 / 喇叭 / 灯光
        │
        ├─ 12V → 5V Buck（≥2A）→ 高边开关 → 交互板 Type-C
        │                              └─ 车辆板 GPIO 控制通断
        └─ 12V → 3.3V Buck（≥1A）→ 车辆板
```

要点：
- 交互板**不要**同时插锂电和车电，AXP2101 会与车辆 DC-DC 打架。
- 拔钥匙后保持 12V 供电 30–300s（车辆板自己做延时），用于上报「已落锁」再断电。
- 静态电流目标 < 3mA，否则一个月掉光电瓶。

## 七、安全红线

1. **48–72V 绝不进 ESP32 任何引脚。** 分压也必须先过 1MΩ 以上电阻网络 + 钳位二极管 + 运放跟随。
2. **感性负载**（电磁锁、喇叭）必须续流二极管 + 光耦/继电器隔离，**不与 MCU 共地**。
3. **行驶中禁止开锁**：车速 > 3km/h 时拒绝一切开锁请求，硬判断，不做提示后放行。
4. **SOC 不要用电压查表硬算。** 磷酸铁锂平台期电压几乎不变，纯电压估算误差可达 30%。优先读 BMS（CAN/485），读不到就明示「估算值」。
5. **远程开锁需鉴权**：时间戳 + 一次性 nonce 防重放，且失败 3 次锁死 5 分钟。
6. 调试串口在生产固件里关闭，防止物理接触后直接发开锁指令。
